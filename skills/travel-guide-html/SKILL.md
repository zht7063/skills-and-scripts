# 图文旅行攻略与联动地图

交付能帮助旅行者选方案、按日执行、临时删减安排的攻略。优先保留用户已有页面、明确偏好与已授权工作；不要将本案例的目的地、节奏、配色或“每段三候选”变成所有旅行的规定。

## 开始与续做

- 从当前对话和项目记录提取：年份和日期、每段出发/到达窗口、人数、交通方式、住宿范围、体力和兴趣、预算、必去点。区分“17:00 后下班”与“17:00 后列车发车”。明显日期笔误可说明合理解释，不能静默改动。
- 用户提供新目的地或返程日期时，更新整个行程依赖：交通、住宿晚数、离站倒推、地图、清单和预算边界。项目旧文档可能过时，以用户最新确认及可验证事实为准。
- 只问阻碍关键决策的缺失信息；其他用显式假设推进。普通旅行调研不必自动升级为深度研究，也不自动开子任务、订票、联系商家或发布网站。
- 延续已有 HTML 时，先定位相关模块与状态，不输出整段 base64。不要为小幅改动重做全页。

## 调查 → 取舍 → 制作

1. 按 [研究与时刻证据](references/research.md) 核对地点、运营、交通与图片。使用当前环境可用的检索工具；已有专门研究技能时依其路由，不把某个插件当作运行前提。
2. 按地理范围安排路线。无车游客避免把远郊散点串成高频打车线路。每天有核心活动，可选项明确标为替代、删减或天气备选。
3. 将时间拆成活动、航行/道路交通、候车/排队、步行到入口、餐饮、休息。说明余量已含还是另加；各段上限相加后检查能否满足总时间窗。船游总耗时不能平均除以岛数当作每岛可用时间。
4. 根据实际产品区分固定集合与自由换乘。只凭历史公告不能承诺目标日随时上船、上岛不限时或返程直达。没有固定停留时长证据时，给“建议预留”，同时指出尚待确认的限制。
5. 新增历史参考路线时，按实际停靠组合识别、标明版本，与既有相同方案合并标注。同步日程和大地图的选择入口；票价拆分时核对套餐包含项，避免重复计费。细则见研究参考。
6. 按 [HTML 与交互验证](references/html-and-interaction.md) 实现日程、地图与方案联动。用户要空间地图时，节点箭头流程图只能作补充。可以使用不按比例的 SVG，但必须标明简化与误差边界。
7. 基于风险验证改动：路线选择是否真正改变日程与地图、跨日是否重复、时长是否相容、离线是否缺图、手机是否能操作。更新受影响记录，交付绝对路径文件链接与必要限制。

## 时间与联动的决策规则

- 使用时间窗，说明发船时刻/返航只是条件示例还是已确认班次。景区实际闭园和交通末班始终优先于示例行程。
- 预留余量必须有用途；不要给同一段重复加“排队 30 分钟”和“总缓冲 30 分钟”。假日排队范围是规划假设，不冒充排队预测。
- 给出延误后的动作：缩短散步、换一家无需久等的餐厅、保留午休、取消夜逛。不要通过延长营业时间、假设一定有末班车来消化延误。
- 高强度前一日可推荐较轻松次日；手动选定的方案优先，提供“恢复自动推荐”。雨天把活动提前到当天可接待时段，避免傍晚临时赶已关门的室内点。
- 同一活动在不同日作替代时，联动提示避免重复；不要擅自禁止用户重复选择。
